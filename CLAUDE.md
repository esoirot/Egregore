# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Shared infrastructure for containerized POC development environments (Windows 11 → WSL2 → Ubuntu → Docker Engine; no Docker Desktop). It is not an application: it holds image definitions (`images/`), project templates (`templates/`), optional services (`services/`), host-side Bash scripts (`scripts/`), tests (`tests/`), and docs. Application code lives in separate project repos generated under `~/projects/`.

Problem it solves: the team builds POCs on arbitrary stacks. Standardize the interface (`dev` entry point, `just` command contract, devcontainer.json), not the stack.

Guiding principle: the Ubuntu host only has git and Docker; everything else (runtimes, the Dev Containers CLI) runs in containers. Source code stays on the WSL filesystem and is bind-mounted to `/workspace`.

## Commands

There is no build system. Tests are plain Bash, given/when/then scenarios:

- `tests/new-project` (~30 s): behavior suite for `new-project` (create, `--from`, `--with`, `--ide`) and `dev update`, against local fixture repos, plus a contract check run for every template found (`check_contract`: with and without `--ide=vscode`, `devcontainer read-configuration` resolves service `dev`, `remoteUser` `dev`, `/workspace` and the `vscode-extensions`; compose service `dev` uses the base image and loads `.env`; the justfile has the `# Team command contract` header and the five recipes; `adopt` is executable). A new template is checked with no test change. Template-specific scenarios (adopt, env-skip) live in `templates/<name>/test`, sourced at the end of the suite (a file that runs no scenario counts as a failure): plain functions plus `scenario` calls, using the suite's helpers (`make_repo`, `fails`, `feature_version`, `just_dry_run`, `$NEW_PROJECT`, `$PROJECTS_DIR`, …). Each sandbox is a copy of the repo's git-visible files with `scripts/dev` stubbed (the real one kept as `scripts/dev.real` for `dev update`) and `code` stubbed. Needs the base and CLI images locally (scenarios run `just` in the base image, `read-configuration` in the CLI image).
- `tests/check-image-tags` (<1 s, no Docker): behavior tests for `scripts/check-image-tags` on throwaway git repos.
- `tests/renovate` (<1 s, no Docker): applies the generic Renovate manager's regex from `renovate.json` to sample lines and to every `renovate:` comment under `templates/`; fails, naming file and line, when a comment yields no version from the line below.
- `tests/dev` (~50 s): real containers. `dev up` cleanup after a port conflict (a blocker container holds the port; minimal project on the base image, no features), a redis service reached by name through `include:`, and a host uid that is not 1000: it builds a throwaway `egregore-test-host-sim` image (CLI image + bash) and runs `scripts/dev up` from it as uid 1001 on a workspace owned by 1001, checking `dev` gets uid 1001 and can write `/workspace`. Cleans up its containers, volumes, the sim image, `vsc-dev-{cleanup,uid}-test-*` images, and the uid-1001 files (removed as root in a container).

No test goes through an IDE GUI: the contract check resolves every template's config with `devcontainer read-configuration`, but VS Code "Reopen in Container" is untested. CI (`.github/workflows/images.yml`) runs `shellcheck --severity=warning` (SC1091 infos from dynamic `source` paths are expected) on `scripts/*`, `tests/*`, `images/*/validate`, `images/*/entrypoint`, `templates/*/adopt`, `templates/*/test` and local feature `install.sh` files, builds and validates every image, runs `tests/renovate` and both test suites, then runs `new-project` for every template, `dev exec just --list` in the result, and `dev down` before the next one (every template publishes port 3000, so a running project makes the next `compose up` fail).

```bash
./scripts/bootstrap                   # host setup: git, Docker Engine + Compose (Docker apt repo), WSL systemd, docker group
./scripts/install                     # check prereqs, add scripts/ to PATH, build + validate every image (PULL_IMAGES=1 to pull from GHCR)
new-project <template> <name> [--from <git-url|path>] [--with postgres,redis] [--ide=vscode]
dev up | shell | exec <cmd> | down | update    # per-project, from the project root
tests/renovate && tests/new-project && tests/dev
```

`bootstrap` and `install` are meant to be idempotent. GHCR is wired but **disabled**: `install` pulls only with `PULL_IMAGES=1` (falls back to building), and CI pushes on `main` only when the repository variable `PUBLISH_IMAGES` is `true`.

## How the pieces connect

- An image is any `images/<name>/` with `Dockerfile` + `image.env` (defines `IMAGE`, versioned tag) + optional executable `validate <image>`. `install` and CI build all of them.
  - `base`: Ubuntu 26.04 pinned by digest, non-root `dev` user (uid 1000; the stock `ubuntu` user is removed to free it), passwordless sudo, git, build-essential, `just`. No language runtime.
  - `devcontainer-cli`: `docker:<ver>-cli` + `@devcontainers/cli` (pinned). Its `entrypoint` script appends the current uid/gid to `/etc/passwd`/`/etc/group` (made world-writable in this throwaway image) when missing, then execs `devcontainer`: the CLI calls `id -un`, and `scripts/dev` runs it as the host user, who has no account in the image. The `image.env` tag follows the CLI version (Renovate bumps both); image changes without a CLI bump keep the tag (its `image.env` has `# tag-guard: off`), and `install` rebuilds locally anyway while GHCR is disabled.
- A template is a `templates/<name>/` directory with a `scaffold/` (that marker is how scripts, `install` and CI find templates; `templates/_shared/` has none):
  - `templates/_shared/`: `compose.yaml` and `.env.example`, identical for every stack. `render` copies it first, then the template's `scaffold/` (a template file of the same name wins). Lock and `dev update` treat these files like scaffold files.
    - `compose.yaml`: top-level `name: {{PROJECT_NAME}}`, service `dev` on the base image, `sleep infinity`, `env_file: .env` (optional; so variables reach every process, not only `just` recipes), port `127.0.0.1:${APP_PORT:-3000}:{{PORT}}` (host side `APP_PORT` for every template; container side from the template's `port` file, default 3000).
    - `.env.example`. The root `.gitignore` ignores `.env.*` but re-includes `!.env.example`, otherwise it is never committed and `new-project` cannot seed `.env`.
  - `scaffold/`: the dev environment, copied into every project (also repos adopted with `--from`) and tracked by `dev update`.
    - `.devcontainer/devcontainer.json`: `dockerComposeFile: ../compose.yaml`, service `dev`, `remoteUser: dev`, the stack as Dev Container Features (pinned versions), `postCreateCommand`. Local features live in `.devcontainer/<name>/` (`devcontainer-feature.json` + `install.sh`, run as root; `_REMOTE_USER` available). A feature that installs a runtime `dev` must write to (gems, Python versions) must not `chown` it to `$_REMOTE_USER`: the CLI remaps `dev` to the host uid after the build and only `dev`'s home follows, so a uid-1001 host (GitHub's runner) got a read-only `/opt/ruby` (`rails: command not found`). Nor make it world-writable: Bundler refuses gems under world-writable directories. Use the `devtools` group: `groupadd --system devtools`, `usermod -aG devtools "$_REMOTE_USER"`, `chgrp -R` + `chmod -R g+rwX` + setgid on directories (supplementary groups survive the remap). Both `ruby` and `uv` do this.
    - `justfile`: the command contract `install`, `dev`, `test`, `lint`, `build` (plus `init` where `postCreateCommand` calls it). Keep recipes generic enough for adopted repos.
    - `.gitignore` for node and fastapi (`gradle init` / `rails new` generate one for java and rails).
  - `starter/` (optional): sample project, copied only into new projects, never with `--from`, never updated. Production `Dockerfile` + `.dockerignore` stub (node, java, fastapi; `rails new` generates Rails's own), README, and the sample app (node: `package.json`, `biome.json`, `src/`, `test/`; fastapi: `pyproject.toml`, `.python-version`, `app/`, `tests/`). Files that only fit the sample app belong here, not in `scaffold/`.
  - `adopt` (optional, executable, idempotent): `adopt <project-dir>`, run by `new-project` (only when it copied `devcontainer.json`) and by `dev update` (when it wrote files). rails: `.ruby-version`; node: `.nvmrc`/`.node-version`; java: `.sdkmanrc` `java=`/`gradle=` plus Maven recipes; fastapi: pip recipes for requirements-only repos. Versions are edited in `devcontainer.json` with `sed`; justfile variants are filled with quoted bash `${var//pat/"$rep"}`, not sed, because they contain `&` (bash 5.2 also expands `&` in unquoted replacements). A variant only replaces the justfile the template copied (detected by its `# Team command contract` header plus a stack marker), never a repo's own.
  - `vscode-extensions`: one extension id per line, for `--ide=vscode`.
  - `test` (optional, sourced, not executable): the template's scenarios for `tests/new-project`, e.g. its `adopt` cases.
  - `env-skip` (optional): service variables `new-project` does not write for this template (rails: `DATABASE_URL`).
  - `port` (optional): one number, the app's container port (`{{PORT}}`, default 3000). `render` validates it (1-65535) before anything is created; the contract check compares it with the published port.
- Templates:
  - `fastapi`: local `uv` feature installs uv 0.12.23 and `uv python install 3.14.8` into `/opt/uv-python` (group `devtools`), sets `UV_PYTHON_INSTALL_DIR` and `UV_LINK_MODE=copy`. `postCreateCommand: just install` runs `uv sync`. `just dev` runs `fastapi dev` without a path so the CLI discovers the app (`main.py`, `app.py`, `api.py`, `app/{main,app,api}.py`, object `app` or `api`); `just build` runs `compileall -x '\.venv' .` on the whole project. Starter dev deps include `httpx2` because Starlette's TestClient deprecates `httpx`; `pyproject.toml` has `package = false` and pytest `pythonpath = ["."]`. `adopt`: a repo with `requirements.txt` and no `pyproject.toml` (uv sync needs one) gets `requirements.justfile` (`uv venv --allow-existing`, `uv pip install -r requirements.txt` and `requirements-dev.txt` if present, ruff via `uvx ruff@<pin>`, no lock check); `uv run` uses the local `.venv` without a project.
  - `java`: official java feature via SDKMAN, Corretto `27.0.0-amzn` (SDKMAN has no Temurin 27), Gradle 9.8.0. `postCreateCommand: just init` runs `gradle init --type java-application --dsl kotlin` with toolchain 27 and `--overwrite` only if no `settings.gradle(.kts)`, `build.gradle(.kts)` or `pom.xml` exists, then appends `.env` to Gradle's `.gitignore`. `adopt` for a `pom.xml` build writes `maven.justfile`: `@MVN@` becomes `./mvnw` (wrapper present) or `mvn` (and `"installMaven": true` is added to the feature), `@DEV@` becomes `spring-boot:run` when the pom uses `spring-boot-maven-plugin`, otherwise a failing message about the main class; its `init` is a no-op because `postCreateCommand` still calls `just init`. The starter `Dockerfile` installs `findutils` in both stages because `gradlew` and the generated `bin/app` need `xargs`, missing from Amazon Linux.
  - `node`: official node feature, Node 26.10.0, pnpm 12.9.1. Starter ships a working app on Node built-ins (`src/app.js` exports `createApp`, `src/main.js` listens on 3000) and `node:test` tests; `postCreateCommand: just install`. `justfile` delegates to `package.json` scripts: `dev` = `node --watch`, `test` = `node --test`, `lint` = `biome check .` (Biome 2.5.15; `biome.json` only sets space indentation, since Biome defaults to tabs), `build` = `node --check` (no bundler).
  - `rails`: local `ruby` feature compiles Ruby 4.0.7 with ruby-build into `/opt/ruby` (group `devtools`, see above) (the official rvm-based ruby feature rejects Ruby 4) and installs `tzdata` (base image lacks it; Rails needs it to boot) and `libpq-dev` (pg gem). `postCreateCommand: just init`: if no `Gemfile`, installs Rails 8.1.4 and runs `rails new . --name=<project> --skip --database=<postgresql if PGHOST is set, else sqlite3>` (keeps scaffold files, adds `!/.env.example` to the Rails `.gitignore`), then `bundle install`. `env-skip` drops `DATABASE_URL`: Rails would merge it into every environment, so `bin/rails test` would use (and wipe) the dev database; with `PGHOST`/`PGUSER`/`PGPASSWORD`, Rails keeps `<app>_development` and `<app>_test` from `database.yml`. `just build` precompiles assets in production mode then clobbers them, because a dev-mode precompile makes `just dev` serve stale assets.
- Services: `services/<name>/compose.yaml` (pinned image by digest, named volume, healthcheck, not published on the host) + `env` (variables). `postgres` (18.6; user/password/db `dev`; `DATABASE_URL`, `PGHOST`, `PGUSER`, `PGPASSWORD`; volume at `/var/lib/postgresql` as the 18+ image expects) and `redis` (8.10.2; `REDIS_URL`). `--with` copies each to `compose.<name>.yaml` and prepends `include:` to the project's `compose.yaml`; the CLI and `docker compose down` follow the include.
- `scripts/new-project`:
  - Options in any order after `<template> <name>`; unknown options, services or IDEs fail before anything is created.
  - `render` builds the full template output in a temp dir, before the project folder is created or cloned (a broken template leaves nothing behind): `_shared/`, `scaffold/` (+ `starter/` unless `--from`), placeholders `{{PROJECT_NAME}}`/`{{IMAGE}}`/`{{PORT}}` by `sed`, `include:` + `compose.<svc>.yaml` + service env in `.env.example` (minus `env-skip`), and for `--ide=vscode` a `customizations.vscode.extensions` block (last `}` of `devcontainer.json` replaced). Placeholders are only ever substituted in rendered files, never in repo code.
  - Create: clone (`--from`) or mkdir, copy rendered files the project lacks (repo files win), run `adopt` if it copied `devcontainer.json` (else print a note), write `.devcontainer/template.lock`, seed `.env` from `.env.example` if missing, ensure `APP_PORT` (honoring `APP_PORT=<port> new-project ...`, default 3000) and service variables (minus `env-skip`), list added files with `--from`, `dev up`, then `code .` for `--ide=vscode` if `code` is on the PATH (else a hint).
  - `template.lock`: `template`, `name`, `services`, `ide` lines and `file <sha256> <path>` for each tracked file (scaffold + service files the project got; not starter files, not repo files), hashed after `adopt`.
  - `--update` (what `dev update` execs, in a project root): re-render without starter, then per file: not in lock but exists → repo's own, skip; new hash == locked → template unchanged, skip (even if you edited it); current == locked → overwrite; edited → write `<file>.template-new`, lock records the offered hash; missing and locked → you deleted it, skip; missing and not locked → add. Runs `adopt` if it wrote files, rewrites the lock, reports only files whose content actually changed (adopted files are rewritten each time but end identical). No lock → error, nothing changed.
- `scripts/dev` runs the CLI image with `/var/run/docker.sock` mounted and `$PWD` mounted at the same path (the CLI passes host paths to the daemon), **as the host user** (`--user $(id -u):$(id -g)`, `--group-add` the socket's gid, `HOME=/tmp`). The CLI's `updateRemoteUserUID` remaps the image's `dev` user to `NEW_UID=<its own process uid>`: run as root, `dev` stayed 1000 and could not write `/workspace` for any host uid other than 1000 (caught on GitHub's runner, uid 1001: `uv sync` failed with permission denied). On a uid-1000 host the remap is a no-op, which hid the bug locally. `--workspace-folder` must come before the exec command. `down` is plain `docker compose down` (works because compose sets `name:`; named service volumes survive). If `devcontainer up` fails, `dev up` runs `docker compose down` and exits 1 with a hint: otherwise a retry starts the half-created container without its port (e.g. after a port conflict). `update` execs `new-project --update`.
- `scripts/install` appends `export PATH="<repo>/scripts:$PATH"` to `~/.bashrc`, using the actual clone location.
- Adding a template or a service needs no script changes; the README sections "Adding a New Template" and "Adding a Service" are the user-facing guides.

## Things to keep in sync

Renovate (`renovate.json`; active once the file is on `main`, since Renovate reads the default branch, and the Renovate GitHub App is installed) opens weekly PRs for every pin below, one per template (`matchFileNames: templates/**`, group name from the path: `{{lookup (split packageFile '/') 1}} template`; majors split out by Renovate), one per dependency elsewhere. Built-in managers cover Dockerfiles (incl. `COPY --from`), compose files, `devcontainer.json` features and the node `version` option (the `devcontainer` manager's file pattern is widened: by default it only scans a root `.devcontainer/`), `package.json`, `pyproject.toml`, `.python-version` (pyenv) and Actions. Other pins under `templates/` are annotated for one generic regex manager: a comment on the line just above, `# renovate: datasource=<ds> depName=<name> [versioning=<v>] [extractVersion=<re>]` (fields in that order; `//` in JSONC files, which the CLI accepts in both `devcontainer.json` and `devcontainer-feature.json`), and the version is the first number on the next line not glued to a letter, digit or dot (`"python3": "3.14"` reads `3.14`; `v1.2` reads nothing; `tests/renovate` checks every comment) (so annotate a line whose first digits are the version, e.g. a `ruff := "ruff@0.16.10"` justfile variable, not a recipe line, since `just` echoes comments in recipe bodies). Tests that check strict JSON use `jsonc_valid`. Remaining regex `customManagers` cover feature options any template may use (`pnpmVersion`, `gradleVersion`) and the images, one manager per dependency: never pick a datasource with a template condition on `matchString` (not available there; everything silently fell back to the first branch, e.g. Gradle and pnpm looked up as Node). When adding or moving a pin, annotate it (or add a manager outside `templates/`) and check it with a local dry run (the local platform ignores the repo config, so pass it as global config):

```bash
docker run --rm -e LOG_LEVEL=debug -e LOG_FORMAT=json -e RENOVATE_CONFIG_FILE=/repo/renovate.json \
  -v "$PWD:/repo" -w /repo ghcr.io/renovatebot/renovate:44 renovate --platform=local --dry-run=lookup
docker run --rm -v "$PWD:/repo" -w /repo ghcr.io/renovatebot/renovate:44 renovate-config-validator renovate.json
```

In the JSON log, the `packageFiles with updates` message lists every detected dependency with its datasource. Not tracked on purpose: the `dev-base` tag, the java `--java-version` major, apt packages.

- **Image tags** live only in each `images/*/image.env`. Tags are versioned; never `latest`. Bump the tag when the image changes: `scripts/check-image-tags <base-commit>` (CI, against the PR base or the previous `main` commit; `fetch-depth: 0`) fails when files in `images/<name>/` other than `image.env` changed and its `IMAGE` line did not. A new image is guarded with no change; an `image.env` with a `# tag-guard: off` line is skipped (`devcontainer-cli`).
- **Image pins**: base image digests in `images/*/Dockerfile`; `@devcontainers/cli` version in its Dockerfile and its `image.env` tag.
- **Service pins**: image tag + digest in `services/*/compose.yaml`.
- **FastAPI template pins**: uv and Python in `devcontainer.json` (`./uv` feature options), `.python-version`, and the `python:<ver>-slim` + `ghcr.io/astral-sh/uv:<ver>` tags/digests in its starter `Dockerfile` (keep all equal); direct dependencies `==`-pinned in `pyproject.toml`; ruff in `pyproject.toml` and `requirements.justfile` (keep equal).
- **Java template pins**: JDK in `devcontainer.json` (SDKMAN id) and the `amazoncorretto` tags/digests in its starter `Dockerfile`; Java major in the scaffold `justfile` (`--java-version`); Gradle in `devcontainer.json` (`gradleVersion`, which `gradle init` copies into the wrapper).
- **Node template pins**: Node and pnpm in `devcontainer.json` (features), `packageManager` in `package.json`, and the starter `Dockerfile` (keep equal); Biome exact in the starter `package.json`.
- **Rails template pins**: Ruby in `devcontainer.json` (`./ruby` feature option), `RUBY_BUILD_VERSION` in `.devcontainer/ruby/install.sh` (must know that Ruby version), Rails in the `justfile` (`rails_version`).
- Templates keep the contract: service `dev`, `/workspace`, `remoteUser: dev`, the five `just` recipes, `env_file` in `compose.yaml`, placeholders rather than hardcoded tags, and a `vscode-extensions` file.

## Conventions

- Scripts are Bash with `set -euo pipefail`, are extensionless, and are executable. `install` checks that `new-project` and `dev` are executable (`-x`).
- Under `set -euo pipefail`, a function or loop whose last command is `[[ ... ]] && cmd` returns non-zero when the test is false and kills the script (also inside `$(...)` assignments and pipelines); use `if`. In tests, `! cmd` never trips `set -e`, and `set -e` is ignored inside `if` conditions (even subshells): use the `fails` helper and the `scenario` runner.
- Stacks change through `devcontainer.json` features, never through manual installs in running containers. Shared changes go in this repo.
